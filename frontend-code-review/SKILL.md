# 敏捷代码审查框架（Skill 版 v6 · 反幻觉强化版）

> 适用框架：Vue 2 (Options API) / Vue 3 (Composition API) / React Hooks
> 设计原则：**深度优先、攻击面思维、数据流追踪、根因导向、反幻觉、先验证再判断、结论收敛、行动导向**
> 核心目标：按任务规模在**单 agent 三视角顺序审查**与**多 agent 并发审查**之间自适应切换，最后统一终审合流，消除重复噪音，输出唯一、清晰、可执行的"行动清单"，并确保每条结论都有代码证据

## 何时使用

- 审查 diff、完整文件、代码片段或仓库快照。
- 用户要求"代码评审 / review / 找问题 / 能不能合并"。

**不适用**：修改代码（用 `frontend-code-modifier`）、纯溯源分析（用 `frontend-code-tracer`）。

## 核心审查哲学

> **表皮问题人人能发现，深度问题才是价值所在。**
> **评审的最终目的不是"找茬"，而是"给出明确的修改指令"。**
> **没有代码证据的结论，宁可不输出。**
> **一条被证伪的 P0 会摧毁整份报告的可信度——准确性 > 数量。**

**全局禁止：**

- ❌ 指出问题但不说明**触发条件**和**实际后果**
- ❌ 无法定位到具体代码行的审查意见
- ❌ "可能"、"也许"等无代码证据的模糊表达
- ❌ 无问题时凑问题（直接输出 🟢）
- ❌ 未验证上下文就断言"缺失/错误"
- ❌ 不同角色对同一问题进行重复描述（必须收敛）
- ❌ **P0/P1 结论未附原始代码引用（必须 3-10 行 + 行号）**
- ❌ **对当前框架不存在的概念提建议（如对 Vue2 项目谈 useEffect）**
- ❌ **为了让报告"看起来有产出"而把 P2 拔高成 P1、P1 拔高成 P0**

## 默认执行模式：按规模自适应（强制）

> 本 skill 命中后，**默认先判定任务规模，再决定是否拆分子 agent**。不要把并发当作默认正确答案。

- **小型 / 中型改动**：默认使用**单 agent 三视角顺序审查**。通常更快，且减少去重、等待、收敛成本。
- **大型 / 跨模块改动**：优先考虑**多 agent 并发审查**，把完整性、正确性、影响面拆开并发执行，再统一终审。
- **用户明确要求启用多 agent 并发**：即使是中型改动，也可启用子 agent，但仍要提醒可能有额外调度成本。

### 三个并发视角

1. **完整性（Agent 1）**：需求是否被完整实现；改动是否覆盖成功/失败/空态/边界态；相关测试、文档、类型、调用入口是否同步。
2. **正确性（Agent 2）**：代码逻辑、类型、语法、异步、状态流、错误处理、安全防护是否存在真实 bug。
3. **影响面（Agent 3）**：共享函数、状态、缓存、storage、路由、API、跨组件调用是否引入副作用、回归或隐式不变量破坏。

### 执行要求

- **单 agent 路径（默认）**：在同一 agent 内按"完整性 → 正确性 → 影响面"顺序独立检查，分别取证，最后统一汇总；不得把三视角揉成一段泛泛而谈。
- **多 agent 路径（仅在值得时启用）**：三个视角并发独立分析，输入相同，禁止相互参考中间结论，最后统一汇总去重。
- **并发工具路径**：即使不启用子 agent，也应并发获取 diff/stat/name-status/check、相关文件读取、符号/调用链/数据流搜索，减少串行等待。
- **IDE / 环境兜底**：如果当前 IDE 或运行环境不支持子 agent，或虽然暴露了子 agent 工具但上层策略不允许默认拉起子 agent，则自动退回单 agent 路径；审查流程不降级，只改变执行方式。
- 三个视角共享同一套证据约束：没有文件、行号、触发条件、实际后果的结论，不进入 P0/P1。
- 终审阶段必须进行**根因合流**：同一问题若被多个视角命中，只保留一条主结论，其他视角仅做引用。

### 何时值得拆分子 agent

命中任一才建议启用多 agent：

1. 变更 `> 300` 行或 `> 5` 个文件。
2. 明显跨模块：组件、store、路由、接口封装、公共工具函数同时改动。
3. 需要三条相对独立的问题链同时追踪，例如：需求覆盖、异步竞态、跨文件副作用都很重。
4. 用户明确要求"多 agent 并发评审"。

命中任一则**不要**拆分子 agent：仅 1-3 个文件、小 diff、单点规则或提示词改动；三个视角会高度重叠；终审去重成本明显高于并发收益；评审目标是快速给出 findings。

### 视角与旧三岗的映射

- 完整性视角吸收原"代码质量"中与需求覆盖、职责边界、测试/文档同步相关的检查。
- 正确性视角吸收原"健壮性与性能"及"安全防护"中所有会形成真实 bug 的检查。
- 影响面视角专门负责跨文件、跨组件、跨状态源的调用链、副作用和回归分析。

## 输入约定（评审前必读）

> 在开始任何评审动作前，先识别用户提交的代码形态，并按对应规则处理。若识别失败，进入"中止评审"流程。

| 输入形态 | 典型特征 | 处理规则 |
| --- | --- | --- |
| 完整文件 | 单个/多个完整文件内容 | 可直接执行第零阶段 4 个 Step |
| Git Diff | `+/-` 行、`@@` 标记 | **只对变更行评审**；对依赖的上下文若不可见，列入"待补充清单" |
| 代码片段 | 函数/组件局部 | 默认假设上下文未知，禁止断言"缺失 xxx"，只能基于片段内可见信息评审 |
| 仓库快照 | 多文件 + 目录结构 | 允许跨文件追踪；调用链/引用关系必须真实存在才可引用 |
| 形态不明 | 无法判定 | 进入【中止评审】流程，要求用户明确 |

**默认假设**：未明确说明时，按"代码片段"处理（最保守模式），避免幻觉。

## 变更规模判定（强制触发 + 流程裁剪）

> **触发语句**：评审输出的第一个引用块必须包含"【本次审查模式：快速 / 标准 / 深度】+ 一句话判定理由"，可与【执行方式】合并在同一引用块内（见输出模板）。
> **未输出该模式判定的评审一律视为无效，必须重来。**

| 规模 | 判定标准 | 模式 | 默认执行方式 | 流程裁剪 |
| --- | --- | --- | --- | --- |
| 小型 | ≤30 行，单文件 | 快速 | 单 agent | 跳过：第零阶段 Step 3、终审第 5 节(根因复盘)、P2 清单 |
| 中型 | 31-300 行，≤5 文件 | 标准 | 单 agent；仅在明显跨模块或用户明确要求时多 agent | 完整两阶段 |
| 大型 | >300 行 或 >5 文件 | 深度 | 优先多 agent；不支持时回退单 agent | 完整两阶段 + 量化分析（高频根因统计） |

### 执行方式判定语句（强制）

评审开头必须明确两件事：

```text
【本次审查模式：快速 / 标准 / 深度】判定理由：...
【执行方式：单 agent / 多 agent / 单 agent-环境兜底】理由：...
```

如果用户明确要求别的输出格式，可以不把这两行放在"第一句话"，但仍必须在输出前部明确说明；不要因为格式硬约束和用户要求冲突而让评审失效。

### 输出介质兼容规则（强制）

> **当前环境已确认支持 Markdown 渲染，默认使用精美表格输出评审结果。**

- 默认目标：用**精美 Markdown 表格**承载 findings 和终审清单，让开发者一眼扫描定位。
- 当前 IDE / 终端支持 Markdown 渲染时，**优先用表格**组织 Findings、终审裁决、问题统计、框架检查等结构化信息。
- 仅当运行环境**明确不支持** Markdown 渲染时，才自动退回纯文本分段格式。
- 无论哪种环境，输出都必须满足：有稳定标题块；每条 finding 可独立扫描；位置、触发条件、后果、证据、建议列齐全；不出现"大段说明 + 少量符号"的半结构化难读格式。

### 问题凸出展示与证据佐证规范（强制 · 两列表结构）

> **核心：整份报告用统一的「两列表」承载——左列是级别/编号，右列是该项的完整内容（概述 + 证据佐证同列，可分行）。**

**1. 两列表结构（唯一默认格式）**

- 全表固定两列：**左列 = 级别/编号**（`总结` / `P0` / `P0-1` / `P1` / `P2` …），**右列 = 内容**。
- **第二列自适应宽**：表头分隔线只写普通 `:---`，不要用超长 `-` 串强制撑宽。
- **分组标题行**：每个级别（`P0`/`P1`/`P2`）单独占一行，右列写该级别一句话说明。
- **具体条目行**：每条问题编号（`P0-1`/`P1-1` …）单独占一行，右列用 `<ul><li>` 列表把各字段分行展示。

**2. 右列内容组织（每条 P0/P1 必附证据，缺证据即降级）**

- 右列用 `<ul>` 包裹，每个字段一个 `<li>`：**概述 → 触发条件 → 后果 → 修改指令**。
- **证据佐证独立分隔**：用一个独立 `<li>` 加 `📌 证据` 前缀，再写 `file:startLine-endLine` + 关键代码片段（行内反引号），并用 `// ⚠️` 指向问题行。
- 某级别无条目时，右列直接写"暂无"。

**3. 优雅约束**

- 无问题不凑数：右列写"未发现阻断问题"即可。
- 级别用图标标记：🔴 P0（必修/阻断）、🟡 P1（强烈建议）、💡 P2（可选），🟢 无问题。
- 不写模糊话，右列每条都要能定位到具体文件行。

### Findings-first 两列表模板（默认推荐）

```markdown
> **【本次审查模式】** 标准 ｜ **【执行方式】** 单 agent

| 级别 / 编号 | 内容（概述 + 证据佐证） |
| :---: | :--- |
| **总结** | ⚠️ 修改后合并：存在一处竞态，修复后可合并（P0×0 ｜ P1×1 ｜ P2×1） |

```

## 框架特化检查清单（按版本激活，避免跨框架幻觉）

> 评审开始时识别框架版本（看 `import vue` / `<script setup>` / `import React` / Options API 写法），**仅激活对应列**。

| 检查点 | Vue 2 | Vue 3 | React Hooks |
| --- | --- | --- | --- |
| 响应式陷阱 | `Vue.set` 漏用、数组下标赋值 | `ref/reactive` 解构丢失响应、`shallowRef` 误用 | — |
| 副作用依赖 | watch immediate/deep | `watch` 源、`watchEffect` 自动追踪 | `useEffect` 依赖数组、闭包陷阱 |
| 生命周期清理 | `beforeDestroy` 清定时器 | `onBeforeUnmount` | `useEffect` 返回清理函数 |
| 组件通信 | `$emit`/`$parent` 滥用 | `defineEmits`/`provide-inject` | props 透传、Context 滥用 |
| 异步竞态 | data 异步赋值覆盖 | 同上 | `setState` 异步 + 已卸载组件 |

## 深度审查盲区清单（高价值，三视角都要带着这份清单看代码）

1. **回滚 ≠ 安全**：看到失败路径调用了 rollback/cleanup 不要就此放过。追问三件事：失败点之前已经落了什么状态？rollback 知道这些状态吗？rollback 自己失败了怎么办？内联清理优于外层 catch-all。
2. **三元/兜底的 falsy 分支**：`x ? a : b`、`x || def`、`x ?? def` 必须显式执行两个分支。fallback 是 `''`/`0`/`'.'`/`[]` 这类"无害值"时，检查它在下游会不会产生无意义副作用。
3. **返回值信息损失**：函数返回 `bool` 而调用方需要知道"什么失败、为什么失败"时，检查调用方能否做出有意义的响应（重试/跳过/报错）。错误细节只 print 不返回，非交互式调用方就拿不到。
4. **布尔组合的对称象限**：看到 `if (!a && !b)` 的防御检查，过一遍其余三个象限是否同样被处理。
5. **跨位置隐式不变量**：同一数据被两处以上使用时，识别它们之间的约束关系，验证本次变更后约束仍成立。

## 第零阶段：强制检查流程（评审前置自律）

> 若信息不足或存在不确定项，**必须按下方"中止评审"模板输出**，不得强行评审。

### Step 1：上下文完整性扫描

> **工具优先级（Vue / React 项目）**：默认使用 `frontend-code-skimmer` MCP 做符号查找、调用链、数据流追踪、影响面评估。仅在 MCP 不可用或非 Vue/React 项目时回退到 `rg` / `sed` / `nl` / 编辑器读取等本地可用方式。
>
> - 找定义/引用 → `skimmer_find_symbol`
> - 追数据流 → `skimmer_trace_data_lifecycle`
> - 看调用关系 → `skimmer_get_call_graph`
> - 评估影响面 → `skimmer_get_blast_radius`
> - 看组件结构 → `skimmer_get_component_outline`

- 搜索相关变量/方法的**所有出现位置**；读取 data/state/props/ref/reactive 定义；读取生命周期钩子 / useEffect；读取**完整**方法实现；查看调用链。

**自检**：信息不确定 → 进入"中止评审"模板。

### Step 2：逻辑推导验证

1. **检查现有防护**：是否已有相同的检查？（提"缺失 xx"之前必须先搜索已有防护，这是假阳性的最大来源）
2. **分析业务场景**：边界情况发生概率？框架是否已处理？
3. **验证技术可行性**：平台兼容性、API 行为。

**自检**：建议是否与已有逻辑重复？不加这个判断**实际**会发生什么？回答不出"实际后果"的建议不要输出。

### Step 3：方案副作用评估（小型模式可跳过）

- 建议方案是否会改变执行顺序或引入新竞态？
- **原则**：当前实现已正确且安全时，不要为了"更防御"而增加复杂度。

### Step 4：自我质疑清单（输出前必答）

- [ ] 我是否已查看足够的上下文？
- [ ] 我提出的"缺失"是否经过搜索验证？
- [ ] 我的建议是否与已有逻辑重复？
- [ ] 我是否过度夸大了风险？
- [ ] **每条 P0/P1 是否都附了原始代码引用？**
- [ ] **我引用的 API/概念是否属于当前框架版本？**
- [ ] **如果作者反问"这条在什么输入下会真实触发"，我答得上来吗？**

**任一答案不确定 → 不要输出该条建议**

### 【中止评审】标准模板（信息不足时强制使用）

```markdown
【中止评审 - 信息不足】

## 当前可见信息
- 输入形态：（完整文件 / diff / 片段 / 不明）
- 已识别框架：（Vue2 / Vue3 / React / 未知）
- 涉及文件：file_a.vue, file_b.ts ...

## 缺失信息清单（按优先级）
1. 【必需】`xxxFunction` 的定义文件（被调用但未提供）
2. 【必需】`store/user.ts` 的 state 结构（影响响应式判断）
3. 【建议】`composables/useXxx.ts` 完整实现（影响生命周期判断）

## 无法评审的具体原因
- （例如：当前只看到事件触发函数，无法判断接收方是否存在竞态）

请补充上述信息后重新发起评审。
```

## 第一阶段：三视角审查（可并发，带收敛机制）

> 审查开始前，先用 1-2 句话识别：**变更意图**、**框架上下文**、**高风险区**。
> **收敛规则**：多个视角发现同一根因，**只由最核心视角详细描述**，其他视角注明"见 [视角名] 第 X 条"，禁止重复阐述。
>
> **证据强约束**：每条 🔴/🟡 必须附 3-10 行原始代码引用（带行号）。**未附证据的条目一律降级为 💡 或剔除。**

### 视角一：完整性（需求覆盖与实现闭环）

**关注点：** 需求是否完整落地（主流程、失败流程、空态、加载态、权限态、边界输入）；改动是否只改表层 UI，遗漏数据层、类型层、测试层、文档层、埋点层或调用入口；命名、职责、复用边界是否支持当前需求；staged/diff 场景下新增逻辑是否只改调用点未改被调方，或只改 happy path 未改失败路径。

```
🔴 严重｜file:line — 问题描述
触发条件：... | 后果：... | 建议：...
证据（file:L-L）：
  ↳ <原代码 3-10 行>
```

### 视角二：正确性（逻辑、运行时与安全）

**关注点：** 异步风险（竞态、并发限制、内存泄漏、定时器清理）；边界值（空值、极端值、快速操作）；错误处理（Promise 捕获、UI 状态回滚、部分失败处理、失败恢复路径的残留状态）；可观测性能问题（O(n²) 遍历、内存泄漏、未清理的 timer/listener）；安全正确性（XSS/注入、权限绕过、敏感信息泄露、危险 URL/HTML/postMessage 是否可被真实利用）；框架正确性（仅按当前框架检查响应式陷阱、生命周期清理、effect/watch 依赖、状态闭包和卸载后更新）。

**收敛要求**：由"需求未完整实现"导致的缺口 → 指向视角一，本视角不重复；本视角只关注**运行时可观测**的稳定性后果。

### 视角三：影响面（副作用、回归与跨文件传播）

**关注点：** 改动是否触达共享函数、公共 hooks、store、context、localStorage/sessionStorage、路由守卫、请求封装、组件协议；新旧行为是否不兼容（参数语义、默认值、返回值、过滤/排序/计数口径变化）；调用链上下游是否同步（调用方假设、类型声明、测试桩、埋点字段、缓存 key、持久化 key）；是否破坏隐式不变量。

**收敛要求**：由单点逻辑错误直接导致的问题 → 指向视角二，本视角只描述**传播范围、回归路径和副作用**。

```
🔴 严重｜file:line — 问题描述
传播路径：... | 影响范围：... | 回归条件：... | 建议：...
证据（file:L-L）：
  ↳ <原代码 3-10 行>
```

## 第二阶段：终审裁决（行动清单生成器）

> **这是开发者唯一需要仔细阅读的部分，因此放在输出最前面。** 评审者扮演"技术负责人"角色，将三视角结果**去重、聚类、排序**，生成最终 To-Do List。三视角原始意见作为"附录"放在终审之后供查证。

### 执行步骤

0. **根因合流（前置）**：若多条问题指向同一根因，必须合并为一条，在根因处标注"表现 ×N"并列出各表现点位。禁止把同一根因的多个表象平铺成多条 P0/P1 凑数。
1. **去重与聚类**：同根因问题合并为一条。
2. **噪音过滤**：剔除"理论存在但实际无影响"、"框架已自动处理"、"过度防御"的建议。
3. **优先级排序**：**P0 (Blocker)** 必修否则不能合并；**P1 (Critical)** 强烈建议修复；**P2 (Nice to have)** 可选优化。
4. **降级规则**：🔴/🟡 默认对应 P0/P1。如降级，必须在该条尾部注明"降级理由：xxx"，否则保持原级。
5. **生成行动清单**：简洁、指令式语言。

## 核心原则回顾

1. **结论唯一性**：同一问题在最终清单只出现一次。
2. **根因合流**：多个表象指向同一根因时，合并为一条并标注"表现 ×N"。
3. **行动导向**：不说"这里不好"，要说"请改成这样"。
4. **噪音过滤**：宁可漏一个无关紧要的建议，不让开发者在垃圾信息中找重点。
5. **证据优先**：无原始代码引用的 P0/P1 一律降级或剔除。
6. **框架忠实**：只用当前框架真实存在的概念评审。
7. **准确性 > 全面性**：一条被证伪的 P0 比漏掉一条 P2 的代价大得多。
8. **并发是手段，不是默认答案**：小任务优先单 agent，大任务才拆子 agent。

# 修改专项检查

只读取与当前症状相关的小节。这些是排查问题的线索，命中关键词不等于存在缺陷。

## Vue 响应式与生命周期

- Vue 2 的对象新增属性和数组下标更新要核对是否经过响应式 API；替换已有响应式属性的整个对象与向对象新增字段不同。
- Vue 2.7 或配置 Composition API 插件的项目可以使用相应组合式 API；不能看到 Vue 2 就要求改回 Options API。
- Vue 3 的 `reactive` 普通值解构、`ref` 解包和 `shallowRef` 更新路径需分别判断。Vue 3.5 的 `<script setup>` 响应式 props 解构受编译器支持，不能与普通 `reactive` 解构混同。
- `watch` 的源、`immediate`、`flush`、`deep` 及清理逻辑要结合实际需求。异步回调中 await 之后的访问不能笼统认为被 `watchEffect` 自动追踪。
- `<KeepAlive>` 的停用不等于卸载。定时器、订阅和恢复逻辑按真实激活/停用/卸载边界核对。
- `nextTick` 解决 DOM 更新时机问题，不能用来掩盖错误状态来源或请求竞态。

## React 状态与副作用

- 确认 props、state、Context 与外部 store 的所有权。函数式更新适用于依赖前值的更新，不能解决所有旧闭包问题。
- effect 依赖与读取值保持一致；先判断某段派生逻辑是否需要 effect，避免为消除依赖警告反复设置 state。
- 开发模式 Strict Mode 的额外 setup/cleanup 用来暴露副作用问题，不能直接认定生产会双发；也不要靠关闭 Strict Mode 修复资源管理。
- 卸载后调用 setState 本身不足以证明内存泄漏。要找到仍存活的订阅、timer、监听器、保留引用或实际错误后果。
- 稳定 key 表示业务身份。静态、不会增删重排的列表使用 index 不自动构成 bug；可编辑、排序或过滤列表则需要验证身份复用。
- 不默认添加 `useMemo` / `useCallback`。先确认计算成本或引用变化确实导致问题，再检查优化是否保留正确语义。

## 异步结果与状态归属

先复现可导致错误的顺序：请求 A → 请求 B → B 完成 → A 完成。查看数据层是否已有去重、取消、序号或 key 隔离。

若预期“最后一次查询拥有页面状态”，需要同时约束结果、错误与 loading：

```text
发起请求时确定身份
  → 完成时验证身份仍有效
  → 有效请求才提交 data/error
  → 有效请求才结束当前 loading
```

- AbortController 只有信号接入实际请求且后续处理尊重失效状态时才有效；取消不等于所有迟到回调都消失。
- 单调序号、请求 key、忽略失效结果、取消请求都是候选方案，按项目能力选用。取消与提交保护有时需要配合，不机械指定一种方案。
- debounce 降低频率，不能保证已有请求按序返回。
- 旧请求的 `finally` 可能提前结束新请求的 loading；旧请求的 catch 可能覆盖新请求的 error。不要只保护成功分支。
- 若多个请求应分别显示结果，应按资源 key 保存；全局“最后一次获胜”可能错误丢弃合法并发结果。
- 乐观更新失败时，回滚不能撤销其他成功操作；依据操作标识或版本恢复对应状态。

## 空值与契约

| 输入 | `x || fallback` | `x ?? fallback` |
| --- | --- | --- |
| `0`、`false`、`''` | fallback | 原值 |
| `null`、`undefined` | fallback | fallback |
| `[]`、`{}` | 原值 | 原值 |

修改兜底表达式前确认业务如何定义“无值”。金额零、关闭开关和空搜索词可能都是有效输入；空数组虽 truthy，却可能是业务空态。

不要用 `as SomeType` 代替解析未知接口响应，不要以静默默认值隐藏协议变化。边界输入的处理方式要与调用方和用户期望一致。

## 组件库、样式与可访问性

- 表单默认值是否响应后续 props、reset 恢复哪个基线、弹窗是否销毁子树，均以实际库版本和包装层为准。
- Portal/Teleport 改变渲染位置；状态是否保留由组件身份和生命周期决定，不能仅凭挂载位置推断。
- 下拉/级联选不中时同时检查值类型、对象身份、异步 options、字段映射和受控协议。
- 样式问题先检查最终元素、class、CSS 层叠、作用域与构建产物。不要直接加 `!important` 掩盖选错节点。
- 改交互时核对按钮语义、可访问名称、焦点恢复、Tab/Enter/Escape 行为及触控范围；按实际受影响操作验证。

## SSR 与缓存

- Next.js 等框架的缓存默认值随版本和路由模式变化；先核对版本、App/Pages Router、Server/Client 边界和调用环境。
- 组件需要交互不意味着应把整个页面都改为 Client Component；把边界放在实际需要的位置。
- 缓存 key 是否包含租户、用户、筛选和分页条件，比“有没有缓存”更能决定串数据的原因。
- 水合不一致要比较首个服务端输出与首个客户端输出，检查时间、随机数、区域设置和浏览器专属值。压制警告不能代替修复不一致。

竞态修复：说明旧请求为何能覆盖当前查询、结果和 loading 如何受同一请求身份约束，列出实际完成的逆序响应测试。若仅做静态检查，就明确没有运行浏览器复现。

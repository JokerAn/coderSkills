仅激活与已确认的框架、版本、业务契约和本次范围相关的检查。

## 版本与框架陷阱

版本证据优先取目标包的 manifest、lockfile 与实际构建配置。manifest 的 `^3.4.0`
不能证明正在运行 Vue 3.4；锁定版本、编译器版本与实验开关可能改变结论。
片段中的 `<script setup>`、Options API 或 hooks 只能识别用法，不能确定精确版本。

| 场景 | 要核实的事实 | 常见误报 |
| --- | --- | --- |
| Vue 2 响应式对象新增属性 / 数组索引写入 | 是否通过 `Vue.set`、`splice` 或整体替换更新；值是否实际参与渲染 | 对原本已声明的属性赋值也要求 `Vue.set` |
| Vue 2 Options API / Vue 2.7 Composition API | 项目实际版本、插件和 API 来源 | 看到 Composition API 就判定为 Vue 3 |
| Vue 3 `reactive` 解构 | 解构的是基本值还是仍为代理的对象，后续是否依赖重新赋值 | 把所有解构都说成响应性丢失 |
| Vue 3.5 `defineProps` 解构 | Vue 与 SFC 编译器版本、实际编译器配置；Vue 3.5 默认支持响应式 props 解构 | 把 `const { id } = defineProps(...)` 一律判为失去响应性 |
| Vue 3.4 及更早的 props 解构 | 是否启用了对应实验转换；是否通过 getter / `toRef` 等访问 | 未核配置就套用版本结论 |
| Vue 3 watch 源 | 是 getter、ref、reactive 对象还是提前求值的基本值；第三方 API 是否接收 getter | 以为 Vue 3.5 解构后传 `watch(id, ...)` 就始终有效 |
| Vue 3 `watchEffect` / cleanup | 依赖是否在首次 `await` 前访问；失效清理在何时注册；具体 API 版本 | 假定异步回调 `await` 后读取的依赖也会自动追踪 |
| Vue 生命周期 | watcher 是否在组件 setup 期间同步创建、资源是否由框架管理 | 对已自动停止的 watcher 一律要求手动 stop |
| React effect 依赖 / 闭包 | 回调读取的值、依赖身份、函数式更新、ref 或外部订阅是否保持最新 | 把 lint 提示直接当作已证实的运行错误 |
| React 卸载后的 `setState` | 是否存在活跃订阅、定时器、外部对象持续持有引用或可观测错误 | 将一次 Promise 完成后更新已卸载组件直接认定为内存泄漏；React 18 已移除旧警告 |
| React Strict Mode | React 版本、开发模式、根节点配置及 effect 是否可重入 | 把开发态重复执行直接描述成生产环境重复执行 |
| SSR / hydration | 实际框架、渲染模式、客户端边界与服务端可达路径 | 项目存在 React 就假设一定 SSR，或把浏览器 API 在客户端的使用判成服务端崩溃 |

`onWatcherCleanup` 从 Vue 3.5 起可用，且必须在同步执行期间注册；watch 回调参数提供的
`onCleanup` 不应与这个 API 的同步限制混为一谈。建议替换 API 前先核对安装版本。

## 异步：验证事件顺序与状态写入

缺少 `AbortController` 本身不是缺陷。结果失效标记、请求序号、串行执行、查询库缓存键、
调用方防重或明确禁止并发的业务约束，都可能使代码正确。
取消请求通常也不是唯一修复：核对取消能否阻止后续转换、异常处理与状态提交。

调查真实竞态时，写出最短事件序列：A 发出 → B 发出 → B 返回 → A 返回。
再分别检查 success、error、loading、finally 路径：过期结果是否仍可覆盖当前状态。
证明存在可达的重叠请求、共享目标状态和缺少有效隔离，才有竞态 finding。

复杂状态链先确定必须保持的关系，再查所有可能破坏它的写入：

- `v-model` 要展开 prop 下传与更新事件回写，连同父级重置、watch、store 和异步回填一起检查；多个入口本身不是 bug，关键是谁有权覆盖当前状态。
- 缓存命中也会写状态。核对键包含哪些影响结果的维度、失效发生在何时，以及旧任务是否还能回填已失效的条目；网络分支的请求序号不一定保护缓存分支。
- debounce、定时刷新和延迟 emit 要核对注册时捕获的值、执行时读取的值与取消时机。重置、路由切换或停用可能早于卸载；有卸载清理不等于这些边界已受保护。

只展开与变更相关的入口和可达组合。若保护确实覆盖整条链，到此排除候选，不继续假设缺陷。

有效保护示例（React）：

```tsx
useEffect(() => {
  let active = true;
  load(query).then(rows => {
    if (active) { setRows(rows); }
  });
  return () => { active = false; };
}, [query]);
```

在已知 `load` 会完成且不会拒绝、组件仅需要当前结果的契约下，这段代码已经隔离过期响应。
不能因为没有 abort 再报“旧响应覆盖”或“卸载泄漏”。若怀疑资源浪费，应另证实可观测成本，
并按用户是否要求优化决定是否输出，不把猜测包装成 bug。

## 保留高价值检查

- **失败恢复**：逐一列出失败前已经写入的状态，确认 rollback 覆盖这些写入；检查回滚本身失败
  是否会留下错误状态。存在 catch 或函数名叫 rollback 不足以证明恢复正确。
- **兜底值**：分别追踪 `||`、`??`、三元表达式两侧；`0`、空字符串、空数组可能具有不同业务语义。
- **布尔组合**：按真实输入域检查组合，不以一个防御分支覆盖所有情况，也不创造不可能的输入。
- **返回值契约**：当返回类型、错误传播或取消行为改变时，读取消费方是否仍做正确决策。
- **性能**：寻找会在真实数据量和交互频率下触发的增长路径；大 O 或“可以 memo”不能单独证明影响。
- **安全**：从不可信来源追踪到危险 sink，并检查编码、清洗、协议或来源校验。权限结论必须区分
  UI 显示与服务端授权，不能把隐藏按钮当成安全边界，也不能假定服务端没有校验。

### 变更引入的跨文件契约破坏

已知 `getPage` 在 `src/api.ts:12` 本次由返回 `res.data.items` 改为返回 `res.data`。
其实际调用方 `src/List.tsx:24` 仍执行 `setRows(await getPage())`，第 31 行 `rows.map(...)`。
接口契约确认响应为 `{ items: Item[], total: number }`，旧版正常返回数组。

> [P1] 列表收到响应对象后无法渲染 — `src/api.ts:12`
>
> 本次将返回值从 `items` 数组改为响应对象，但列表页仍将结果直接写入 `rows` 并调用
> `rows.map`。每次正常加载该关键列表页都会发生类型错误，页面无法展示。
> 请同步修改消费方，或保持原函数的数组返回契约。依据为变更行与 List 的实际调用链；
> 结论来自静态分析，尚未运行页面。

根因定位在变更处，后果可位于未改动文件。若列表不是关键流程、影响范围有限，应结合实际影响
使用 P2，不能凭示例标签机械套级别。

### 有业务边界的普通缺陷

已知优惠值允许 `0` 表示免单，默认值是 100；本次在 `src/Price.vue:20` 将
`discount ?? 100` 改为 `discount || 100`，下游仅用结果展示金额，不参与实际扣款。

> [P2] 合法的零折扣被显示为默认值 — `src/Price.vue:20`
>
> 免单订单的 `discount` 为 0，本次使用 `||` 会把它替换成 100，导致展示的应付金额错误。
> 改回仅对 null / undefined 兜底即可。其他调用路径不受此条件影响。

如果该值实际决定扣款金额而非只影响展示，需要据实重新判断严重性。
